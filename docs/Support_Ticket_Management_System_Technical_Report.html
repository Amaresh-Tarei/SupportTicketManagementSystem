3 Core Domain Logic & Business Rules Implementation

All business rules are enforced at the service layer to ensure data integrity regardless of whether requests originate from the Web UI, API tests, or external integrations:

Rule 1: Closed Tickets Are Immutable

Once a ticket reaches Closed status, neither its metadata (Title, Description, Priority, Assignee, DueDate) nor its status can be modified. Attempts return HTTP 400 Bad Request with a clear validation message.

Rule 2: Critical Priority Requires Due Date

Creating or updating a ticket with Priority == Critical mandates a non-null DueDate. Submitting without a due date throws a BusinessRuleException.

Rule 3: Due Date Cannot Precede Creation Date

During ticket creation, DueDate cannot be in the past (before UTC today). During updates, DueDate cannot precede the ticket's original CreatedDate.

Rule 4: Disallow Direct Transition from Open to Closed

Tickets cannot leap directly from Open to Closed without active handling. A ticket must first transition through InProgress or Resolved before closure.

Rule 5: Automatic ResolvedDate Stamping

When a ticket status transitions to Resolved, the system automatically stamps ResolvedDate with the exact UTC timestamp.

Rule 6: Reopening Resets ResolvedDate

If an issue recurrence forces a ticket from Resolved back to Open or InProgress, ResolvedDate is automatically reset to null.

Rule 7: Immutable Audit Trail of Status History

Every status change generates a persistent record in TicketStatusHistories capturing OldStatus, NewStatus, ChangedDate, and ChangedBy.

4 Database Design & Schema

The schema is normalized, indexed for search, and linked with cascade constraints:

Table Primary Key Foreign Keys Key Columns & Constraints
Tickets Id (INT IDENTITY) None TicketNumber (Unique, NVARCHAR(50)), Title (150), Status (Enum), Priority (Enum), CreatedDate, DueDate, ResolvedDate
TicketComments Id (INT IDENTITY) TicketId → Tickets.Id CommentText (NVARCHAR(1000)), CreatedBy (100), CreatedDate (UTC) (Cascade on Delete)
TicketStatusHistories Id (INT IDENTITY) TicketId → Tickets.Id OldStatus (Enum), NewStatus (Enum), ChangedDate (UTC), ChangedBy (100) (Cascade on Delete)

5 RESTful API Specifications

Method Endpoint Purpose Status Codes
GET /api/dashboard/summary Aggregated operational metrics (Total, Open, InProgress, Resolved, Closed, Critical, Overdue) 200 OK
GET /api/tickets Paginated ticket list with search, status/priority filters, date ranges, and sorting 200 OK
GET /api/tickets/{id} Retrieve ticket by primary key with comment count 200 OK, 404 Not Found
POST /api/tickets Create a new ticket with automatic ticket number generation (TKT-XXXX) 201 Created, 400 Bad Request
PUT /api/tickets/{id} Update existing ticket fields (validating closed status & critical due dates) 200 OK, 400 Bad Request, 404
PATCH /api/tickets/{id}/status Execute status transition and record audit history entry 200 OK, 400 Bad Request, 404
DELETE /api/tickets/{id} Remove ticket and cascade delete comments and history 204 No Content, 404
GET /api/tickets/{id}/comments Retrieve chronological comments for a ticket 200 OK, 404 Not Found
POST /api/tickets/{id}/comments Add a new comment authored by team member 201 Created, 400, 404
GET /api/tickets/{id}/status-history Retrieve complete immutable audit trail of status transitions 200 OK, 404 Not Found

7 Frontend Engineering & User Experience

The frontend architecture adheres to Clean UI principles, emphasizing accessibility and performance:

  • Atomic UI Components: Reusable badges (StatusBadge, PriorityBadge), loading indicators, modal dialogs (ConfirmModal, StatusChangeModal), and alert banners.
  • Dynamic Filtering & Pagination: Real-time search debouncing, multi-criteria filter controls, and client-side pagination synchronized with backend query parameters.
  • Audit History Timeline: Visual timeline component tracing every historical status change with user attribution and relative timestamps.
  • Robust Error Feedback: Form field validation errors and server-side business rule exceptions are captured and displayed in contextual banner notifications.

How to Run Locally from Scratch

  1. Clone Repository: 
    git clone https://github.com/Amaresh-Tarei/SupportTicketManagementSystem.git
  2. Backend Startup: 
    dotnet run --project backend/SupportTicketManagementSystem.API/SupportTicketManagementSystem.API.csproj --urls "http://localhost:5000"
  3. Frontend Startup: 
    cd frontend && npm install && npm run dev
  4. Run Automated Tests: 
    dotnet test backend/SupportTicketManagementSystem.Tests/SupportTicketManagementSystem.Tests.csproj
